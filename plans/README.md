## Recommended execution order

1. **001** first — it creates `src/lib/motion.ts` and the `--ease-out` CSS token
   that 002 and 003 both prefer to import from. Landing it first lets the other
   two reference the shared `EASE_OUT` instead of re-declaring it.
2. **002** and **003** — independent of each other; run in either order.

## Dependencies

- 002 and 003 each say "import `EASE_OUT` from `../lib/motion` if plan 001 is
  done; otherwise declare it locally." So they are **not hard-blocked** by 001 —
  they only read cleaner after it. If you execute 002 or 003 before 001, use the
  local-const fallback each plan describes, then let 001's cleanup sweep fold them
  into the shared module.

## Context

Full audit (2026-07): the codebase's motion is already in good shape — one
consistent strong ease-out curve, correct dialog origins, `prefers-reduced-motion`
handled globally via `MotionConfig reducedMotion="user"` plus a CSS block,
interruptible `AnimatePresence` dialogs, no `ease-in`, no `scale(0)`, no
`transition: all`, no animated layout properties, and no motion on
keyboard/high-frequency actions (Tailwind v4 also auto-gates `hover:` behind
`@media (hover: hover)`). These three plans are the only meaningful leverage found,
all LOW severity: 001 is maintainability, 002 is a delight add, 003 is a small
cohesion fix.
