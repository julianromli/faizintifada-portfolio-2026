# React Improvement Plans

Generated by `improve-react` against commit `318741a`, using React Doctor
v0.9.13 as machine evidence plus a senior audit for leverage. Each plan is
self-contained — an executor with zero prior context can run it. Plans 001-015 are
implemented (see "Implementation notes" at the end); **016 is written but not yet
implemented.**

These live in `react-plans/` rather than `plans/` because `plans/` already holds
the animation roadmap (001-003) from a previous `improve-animations` run.

## Baseline

React Doctor scored the repo **59/100 ("Critical")** with 55 diagnostics across
24 files. **24 of those 55 were verified as over-reports on this codebase** and
are not planned (see "Rejected" below). The real weight is mostly *beyond* the
scan, concentrated in the ~365-cell GitHub grid on the homepage, keyboard access
on the revenue path, and the absence of an error boundary.

## Not planned this round

These were vetted and confirmed real, but were not selected:

- **Coupon → free-fulfillment path.** `POST /api/coupon/validate`
  (`server/routes/uikit.ts:14`) is unauthenticated and unthrottled — there is **no**
  rate limiting anywhere in the repo — and answers valid/invalid distinguishably.
  A `fixed` coupon ≥ the checkout price makes `computeDiscountedAmount`
  (`server/lib/coupon.ts:26`) return 0, which routes to `startFreeCheckout` and
  emails the Access Token with no payment. `couponPayloadSchema` caps `percent` at
  100 but leaves `fixed` unbounded, and `coupons` has no redemption cap or email
  binding (`src/db/schema.ts:94`). This holds regardless of how Mayar payments are
  fulfilled. **Highest-severity finding still open.**
- **Webhook handler — status unconfirmed, do not act on this without checking first.**
  `isPaidStatus` (`server/lib/mayar.ts:96`) is a **deny**-list, so any Mayar status
  outside five known strings reads as paid, and two `amount === 0` bypasses at
  `server/routes/uikit.ts:103` and `:118` skip the amount check.
  **However**: the repo owner states Mayar is integrated over its API, not webhooks.
  `fulfillPaidOrder`, `getPayment` and `isPaidStatus` have exactly one caller each —
  the handler at `server/routes/uikit.ts:117-127` — and `markOrderPaid`
  (`server/lib/fulfillment.ts:20`) is the only writer of `status: 'paid'`. So either
  the webhook *is* registered (in which case invert the deny-list to an allow-list),
  or it is unused and the right move is deleting the handler rather than hardening
  it. The route is mounted either way (`server/app.ts:268`).
  **To settle it**: check `/admin/orders` — if paid Buyers show `paid`, the webhook
  fires; if they show `pending` with no `emailSentAt`, it does not.
- **No security headers** (`server/app.ts`) — no CSP, `frame-ancestors`,
  `Referrer-Policy`, or `X-Content-Type-Options` on any of the three entrypoints;
  `hono/secure-headers` is never imported. Cheap, and it blunts the next item.
- ~~**`src/lib/admin-api.ts:21`** stores the raw `CMS_ADMIN_TOKEN` env secret in
  `sessionStorage`.~~ **Now planned as [016](016-admin-session-cookie.md)** (not yet
  implemented). Original note: XSS grants permanent full CMS access,
  order PII, and coupon creation — unrevocable without a redeploy.
- **`server/lib/checkout.ts:81`** sends the fulfillment email before
  `markOrderPaid`, so a failed mark leaves the buyer holding the email while
  seeing an error that drives a duplicating retry.
- Unannounced error containers on the two public forms
  (`CoachingFormDialog.tsx:439`, `TestimonialFormDialog.tsx:333`) — same fix shape
  as plan 009.
- `ToolsStack.tsx:114` (one `<button>` wrapping eight cards → concatenated
  accessible name, `aria-controls` pointing inside itself), `Hero.tsx:37`
  (auto-advancing carousel with no pause control, WCAG 2.2.2),
  `TestimonialFormDialog.tsx:259` (`role="radiogroup"` with no arrow keys),
  `App.tsx:24` (no skip link, route changes not announced),
  `UiKit.tsx:279` (six full-size screenshots into ~200px thumbs),
  `LazyMotionProvider.tsx:2` (`domAnimation` statically imported, so `LazyMotion`
  splits nothing).
- `no-giant-component` ×5, `no-high-complexity-react-function` ×3,
  `duplicate-jsx-subtree` ×2 — real shapes, but four of the five giants are on the
  cold single-admin routes and splitting a 458-line form carries more regression
  risk than it removes.

## Implementation notes (executed 2026-09-03, on top of `318741a`)

All 15 plans are implemented. `tsc --noEmit` and `bun run build` both pass.

**Result**: score **59 "Critical" → 63 "Needs work"**, diagnostics **55 → 41**,
**errors 5 → 0**. Exactly the 14 predicted diagnostics cleared, and no new ones
introduced.

Three places where the implementation deviated from the plan as written:

- **002** — the plan's `calc()`-string variant was **not** used. Motion writes the
  whole `transform` property, so a Tailwind `-translate-x-1/2` class on the same
  element would be overwritten, and `calc()` strings do not interpolate reliably
  under a spring. Shipped the plan's documented fallback shape instead: an outer
  `m.span` pinned at `left-0 top-0` that springs `x`/`y` in pixels, wrapping a
  plain inner `<span>` that carries the static `-translate-x-1/2`
  (and `-translate-y-full` when placed above). `transformOrigin: '0% 0%'` makes
  the pill scale out of the hovered cell. No layout property is animated.
- **001/003/004** — adding the roving-tabindex handler and the
  `IntersectionObserver` pushed `GithubGraph` past 300 lines and introduced a
  `no-giant-component` diagnostic. Extracted both into module-scope hooks in the
  same file (`useOnScreen`, `useRovingGridFocus`) to clear it.
- **007** — reading `triggerRef.current` inside the effect cleanup tripped
  `exhaustive-deps` ("your cleanup may read the wrong node"). The trigger element
  is now captured into a local at effect setup and the cleanup focuses that.
